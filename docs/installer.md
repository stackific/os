# Installer

`stackific-installer` installs Stackific OS from a live session into a drive's free space, next to what is there, or onto a whole drive, which it erases. It is one Rust program for both bases, with a [ratatui](https://ratatui.rs) text interface and an unattended mode that reads the same answers from a TOML file. Its crate is `installer/`; the packages are `arch/packages/stackific-installer/` and `fedora/packages/stackific-installer/`. It ships on all four images: the x86_64 ones since task 012 (Arch) and task 014 (Fedora), the aarch64 ones since task 018. The installed drive starts on its own, through Limine from our ESP (task 013 on Arch, task 014 on Fedora). Next to Windows (task 015) it confirms BitLocker before writing, refuses Intel RST RAID members and BIOS-mode Windows with guidance, and adds Windows to Limine's menu; the user page is `site/src/content/docs/user/windows.md`.

## Build, test, try

```sh
just installer test           # unit, navigation and snapshot tests (pre-commit, and the check workflow)
just installer lint           # cargo fmt --check, then clippy with warnings as errors
just installer demo           # every screen and a simulated install: no root, no disk
just installer demo --slow    # all motion ten times slower, to review it frame by frame
just installer demo --console # the console's screens (ASCII markers, Reduced motion)
just installer build          # a debug build in installer/target/
```

The recipes use the pinned toolchain from `just rust install` (Rust 1.99.1, rustup 1.29.3, in `.tools/rust/`), which `just setup` installs; `just doctor` prints its `rust:` line. The images build with their base's own `rust` package, the same release.

The image tests are in [arch-iso.md](arch-iso.md) and [fedora-iso.md](fedora-iso.md): `just arch test` checks the launcher, Disks and Plasma's GTK integration in the live session (`just fedora test` the launcher, the console path's units, Disks and GNOME's dash), on both architectures, and `just arch test-install` and `just fedora test-install` run real installs in a VM, then boots the last one from its disk alone with the install boot's firmware variables (`tests/vm/installed.sh`): the firmware entry, Limine's menu (`limine.png`), the kernel command line, the ESP's files, stackific-boot's hook (a reinstall of the image's `limine` package, which the recipe copies onto the ESP with `mcopy`), the system settings, the login screen, and the keyboard layout in MangoWM (`mmsg get keyboardlayout`) and Plasma (`org.kde.KeyboardLayouts.getLayoutsList`) or GNOME (`org.gnome.desktop.input-sources sources`). On Fedora it also checks SELinux (enforcing, no label `restorecon` would change), that no GRUB is left, and stackific-boot's kernel-install plugin: a second kernel added and removed with `kernel-install`, and the kernel package reinstalled offline from the ESP with `dnf5`, each time with the Windows entries kept after the kernels.

The Windows cases in `tests/vm/install.sh`, on both bases:

- **BIOS-mode Windows**: an MBR table with a BitLocker volume in a type 7 partition; the free-space run exits 2 naming `MBR2GPT.EXE`, and the table is unchanged.
- **BitLocker**: one of cryptsetup's test images, volumes Windows made (`bitlk-aes-xts-128.img`: a passphrase and recovery key `64311DEA`), written to the Windows-like table's partition 3. The archive's URL and SHA-256 are pinned in `tests/vars.just`; the recipes pass them as `BITLK_IMAGES_URL` and `BITLK_IMAGES_SHA256`, `boot.sh`'s `asset` downloads and checks it into the out folder (kept for the next run), and `vm_put` sends it to the guest as base64 in a here-document. Without the confirmation the run exits 2 naming `vda3` and the key ID; with `bitlocker = "I have my key"` it installs, and the volume's first 100 MiB still match the image.
- **A fake Windows**: Limine's program as `EFI/Microsoft/Boot/bootmgfw.efi` on the Windows-like ESP, an empty `BCD`, and a "Windows Boot Manager" firmware entry made with efibootmgr. After the install the ESP's files are unchanged, `BootOrder` starts with "Stackific OS" then "Windows Boot Manager", and `limine.conf` has both Windows entries with the ESP's PARTUUID.
- **Both entries start it**: at the end of `tests/vm/installed.sh`, a `limine.conf` beside the fake loader starts the installed kernel from our ESP (`guid(<PARTUUID>)`) with `stackific.test=windows` added. Picking "Windows" in Limine's menu (key presses after OVMF starts an entry) restarts into the firmware's "Windows Boot Manager" (`BootCurrent`), and "Windows, started directly" reaches the same marker from our entry. Real Windows with BitLocker stays on the real-hardware checklist.

`just arch screenshots` (not in CI) boots the ISO with a blank 64 GiB disk and drives the real installer by key presses (`tests/vm/screens.sh`): from MangoWM's launcher: Drive with the disk an Intel RST RAID member (an imsm container `mdadm` makes with `IMSM_NO_PLATFORM=1 IMSM_DEVNAME_AS_SERIAL=1`), then through BitLocker to a free-space install next to the Windows-like table, a terminal too small and a stopped erase, then on the console from the Install target through an erase. It saves a PNG of each screen in `.build/arch/<arch>/screens/`; `just site screenshot` turns them into the prompt trail's WebP files. Before each desktop shot it switches to workspace 2 and back (Ctrl+2, Ctrl+1), so MangoWM repaints the whole screen: on the VM's software renderer it can leave stale regions after small redraws. Then it waits until two dumps 2 s apart match.

## What it does

1. **Checks**, before any screen (exit 2 with one line on stderr): running as root, booted in UEFI mode, a known base (os-release's `ID_LIKE`), and that base's live root mounted.
2. **Answers**, from the screens or from `--config <file>`; both paths run the same checks (below). Then, on every listed drive except one an erase removes:
   - **BitLocker** (`installer/src/bitlocker.rs`): each partition `blkid -p` calls `BitLocker`, classified by `cryptsetup bitlkDump`'s protectors: a clear key means suspended (Windows starts without asking), a TPM protector means Windows will ask for the recovery key (Secure Boot is off), otherwise a password, smart card or startup key unlocks it as before. The recovery key IDs are the recovery-passphrase protectors' GUIDs, first 8 characters in uppercase, as Windows shows them. Metadata that cannot be read counts as armed with no known key. Any volume needs the typed confirmation `I have my key` (the BitLocker screen, or `[disk] bitlocker`); without it the unattended run exits 2 and lists each volume.
   - **Windows** (`installer/src/windows.rs`): each EFI System Partition (lsblk's `PARTTYPE`) is mounted read-only (`ro,nosuid,nodev,noexec`) at `/run/stackific-installer/esp` and looked at for `EFI/Microsoft/Boot/bootmgfw.efi`, then unmounted; one already mounted is read where it is. Then whether `BootOrder` holds an entry described "Windows Boot Manager" (ignoring case, as Limine matches it) on one of those ESPs. The screens look when Confirm opens; the install uses that.
3. **Disk step**, shared by both bases:
   - Erase: `sfdisk --wipe always --wipe-partitions always` with a new GPT: partition 1, 4 GiB, EFI System, named `Stackific OS boot`, at 1 MiB; partition 2, Linux filesystem, named `Stackific OS`, to the last usable sector rounded down to 1 MiB. The script gives `first-lba:` and every start and size in sectors (the drive's logical sector size, from lsblk's `LOG-SEC`), because sfdisk aligns only values it picks itself, and some drives report an I/O size that would move its defaults.
   - Free space: `sfdisk --append --wipe never --wipe-partitions always` with the same two partitions at explicit sectors inside the largest 1 MiB-aligned gap, in one write. Every existing entry stays byte-identical.
   - The Confirm screen shows these exact places (`disk::layout`), and the install writes them.
   - `udevadm settle`, then the new partitions' device paths from `lsblk` by their start (never predicted from numbers).
   - Encryption (BT-09, task 016), always: `cryptsetup luksFormat --type luks2 --batch-mode --key-file -` on the system partition with cryptsetup's defaults (argon2id, 2 s, `aes-xts-plain64`), then `cryptsetup open` as `stackific-installer-root`; the login password is the passphrase, on stdin without a newline (`--key-file -` would keep one). btrfs and every later step use `/dev/mapper/stackific-installer-root`. After the final unmount, also after a failure or a stop, the installer closes the mapping (`cryptsetup status`, then `close`).
   - `mkfs.fat -F 32 -n STACKIFIC` on the ESP and `mkfs.btrfs -f -L stackific` inside the LUKS2 container (labels from os-release's `ID`).
   - The subvolumes, flat siblings of `@`, all mounted with `noatime,compress=zstd:1`; `@libvirt` and `@swap` get `chattr +C` (NOCOW):

     | Subvolume     | Mount point               |
     | ------------- | ------------------------- |
     | `@`           | `/`                       |
     | `@home`       | `/home`                   |
     | `@root`       | `/root`                   |
     | `@srv`        | `/srv`                    |
     | `@cache`      | `/var/cache`              |
     | `@tmp`        | `/var/tmp`                |
     | `@log`        | `/var/log`                |
     | `@swap`       | `/swap` (empty for now)   |
     | `@flatpak`    | `/var/lib/flatpak`        |
     | `@libvirt`    | `/var/lib/libvirt/images` |
     | `@containers` | `/var/lib/containers`     |
     | `@docker`     | `/var/lib/docker`         |

   - `@` at `/run/stackific-installer/target`, the other subvolumes under it, and the ESP at its `/boot` (`umask=0077`).
4. **Copy**: `rsync -aHAXx --numeric-ids --info=progress2 --no-inc-recursive --exclude=/boot/ --exclude='/dev/*'` from the live image's pristine root, the lower layer of the live overlay (Arch: `/run/archiso/airootfs`, archiso's squashfs; Fedora: `/run/rootfsbase`, dracut dmsquash-live's erofs image). `--no-inc-recursive` makes the overall percentage count the whole copy, so it only grows. `/boot` is empty in the live root and is the FAT ESP in the target, which takes no owners, ACLs or xattrs. `/dev` keeps only the folder: kiwi leaves unlabelled device nodes in Fedora's live root, and under SELinux rsync may not strip the label their copies get (`fremovexattr … security.selinux … Permission denied`, exit 23); the running system mounts devtmpfs there.
5. **System**: `/etc/fstab` by UUID (twelve subvolume lines and `/boot`); `/etc/crypttab` with the container (`luks-<uuid> UUID=<uuid> none`), which Fedora's dracut copies into the initramfs, so it adds no unlock job of its own beside systemd's; `systemd-firstboot --root --force` for the timezone, the computer name and the console keymap (the first `kbd-model-map` line for the XKB layout with no variant, `us` when none); `/etc/X11/xorg.conf.d/00-keyboard.conf` in the format `localectl set-x11-keymap` writes.
6. **User**: `userdel --root … --remove live` first, so ours gets uid 1000; `chroot <target> useradd --create-home --groups wheel` (not `--root`: Fedora's useradd copies `/etc/skel` only that way); on Fedora, `setfiles` on the target's `/etc` (useradd rewrites the account files with the label `etc_t`, because the live system's policy has no rules for paths under the target, and chpasswd runs in SELinux's `passwd_t`, which may write them only as `passwd_file_t` and `shadow_t`); the password through `chpasswd --root … --crypt-method YESCRYPT` on stdin, which hashes it with libxcrypt instead of PAM (pam_unix fails under `--root` on Fedora); `usermod --root … --lock root`; and `~/.config/mango/config.conf` with `source=/etc/mango/config.conf` and `xkb_rules_layout=<layout>`, so MangoWM's stock config stays as packaged with our layout on top.
7. **Live state**: `/etc/sysusers.d/stackific-live.conf` removed, and greetd's `[initial_session]` (the autologin) removed with every other line kept; then the base's own step. Arch removes `/etc/mkinitcpio.conf.d/archiso.conf` and the live image's `/etc/pacman.d/hooks/stackific-vmlinuz.hook` (aarch64's kernel copy for mkarchiso) and runs `pacman --sysroot <target> -Rns stackific-installer`, so the installed system has no installer and no launcher; `limine` and `efibootmgr` stay, because the explicitly installed `stackific-boot` needs them. `/etc/machine-id` stays `uninitialized` (Arch) or empty (Fedora; kiwi empties it), so systemd sets it on first boot, and the locale stays the live image's.
   Fedora first mounts `proc`, `sysfs`, `/dev` and `/run` (not recursively, so the target's own mount under `/run` stays out) into the target, as arch-chroot does, for rpm's scriptlets and the chroot in step 8; then `dnf5 --installroot=<target> --setopt=protected_packages= -y remove stackific-installer grub2-efi-x64 grub2-efi-x64-cdboot grub2-efi-x64-modules` (on aarch64 `grub2-efi-aa64`, `-cdboot` and `-modules`), offline (GRUB's packages mark themselves protected in `/etc/dnf/protected.d/`, which only this removal lifts), which also takes what only those needed (`clean_requirements_on_remove`). The installed system has no installer, no launcher and no GRUB, so GRUB's kernel-install plugins never run there; `stackific-boot` is named in the image, so it stays with `limine` and `efibootmgr`.
8. **Boot loader**, after the live state so the initramfs is built without archiso's drop-in (Arch) and without GRUB's plugins (Fedora):
   - Limine's program, `<target>/usr/share/limine/BOOTX64.EFI`, to `/boot/EFI/limine/BOOTX64.EFI` (the firmware entry's loader) and `/boot/EFI/BOOT/BOOTX64.EFI` (the firmware's fallback path, which starts the drive when its entry is lost). On aarch64 the file is `BOOTAA64.EFI`, at the same two folders (`boot::EFI`, chosen when the installer is built; UEFI's removable-media name for the architecture), here and everywhere below. Both on our ESP only. It comes first, because Fedora's kernel-install plugin writes `limine.conf` only on an ESP that has it.
   - The kernel and initramfs, per base (`Base::initramfs`). Arch runs mkinitcpio's own pacman-hook script in the target, `arch-chroot <target> /usr/share/libalpm/scripts/mkinitcpio install`, with every `usr/lib/modules/*/vmlinuz` on stdin, as pacman does when it installs a kernel: `/boot/vmlinuz-linux` and `/boot/initramfs-linux.img` on the ESP, from mkinitcpio's default preset (no fallback image) and default hooks (`systemd`, with the CPU's microcode prepended). From then on, mkinitcpio's pacman hooks keep both files current; no unified kernel image. Arch Linux ARM's `linux-aarch64` has no `usr/lib/modules/*/vmlinuz` for that script: the package itself installs `/boot/Image`, which mkarchiso empties from the live root, so on aarch64 the installer copies the kernel from the boot medium (`/run/archiso/bootmnt/arch/boot/aarch64/vmlinuz-linux`, the live hook's copy of `/boot/Image`) to `/boot/Image`, the path the package owns, and runs `mkinitcpio -P` in `arch-chroot`, whose `linux-aarch64` preset writes `/boot/initramfs-linux.img`; later `linux-aarch64` upgrades write `/boot/Image` themselves. Arch first writes `/etc/mkinitcpio.conf.d/stackific.conf`: Arch's default hooks plus `sd-encrypt` after `block` and stackific-boot's `stackific-boot-failure` last (the installer writes it, not a package, whose drop-in would sort after archiso's and change the live image's initramfs). Fedora writes `/etc/kernel/cmdline` (`boot::cmdline`) and runs `chroot <target> kernel-install add <version> /usr/lib/modules/<version>/vmlinuz` for every kernel, as the kernel package's scriptlet does: Fedora's `50-dracut.install` builds `/boot/initramfs-<version>.img` (hostonly, no rescue image; it adds `systemd-cryptsetup` itself, because the root's device stack has `crypto_LUKS`, and stackific-boot's `99stackific-boot-failure`), and stackific-boot's plugin copies the kernel to `/boot/vmlinuz-<version>` and writes `limine.conf` (below).
   - Windows, when found: Limine's entries from `boot::windows_entries`, after the system's. "Windows" (`protocol: efi_boot_entry`, `entry: Windows Boot Manager`) sets BootNext and restarts, so the firmware starts Windows itself and BitLocker sees no change when Limine is updated; it is written only when the firmware has that entry, because Limine stops with an error when it cannot find it. "Windows, started directly" (`protocol: efi`, `path: guid(<PARTUUID>):/EFI/Microsoft/Boot/bootmgfw.efi`), one per Windows ESP, numbered after the first, for when the firmware entry is gone; its comment says BitLocker may ask for its key. Arch appends them to `limine.conf`; Fedora writes them to `/etc/kernel/limine-windows.conf` before kernel-install runs, and stackific-boot's plugin appends that file each time it writes `limine.conf` (Limine has no include). Nothing is written to Windows' ESP, and its firmware entry stays.
   - Arch: `/boot/limine.conf`, the ESP's root, which Limine searches after its program's own folder, so one file serves both copies: `timeout: 3`, `interface_branding: <NAME>`, and one entry `/<NAME>` with `path: boot():/vmlinuz-linux` (aarch64: `boot():/Image`, which Limine's `linux` protocol takes as is), `module_path: boot():/initramfs-linux.img` and `cmdline: rd.luks.uuid=<luks uuid> root=/dev/mapper/luks-<luks uuid> rootflags=subvol=/@ rw quiet` (`boot::cmdline`; `quiet` leaves the passphrase prompt alone on the console; aarch64 adds `console=tty0`, because Linux there makes the serial port in ACPI's SPCR table, which QEMU, UTM and many boards have, the console when the command line names none, and systemd would ask for the passphrase on it): the systemd initramfs unlocks the container and names it `luks-<uuid>`; root names the mapping, not btrfs' UUID, so a failed unlock fails the root mount at once instead of after the 90 s device timeout. The paths are fixed, so a kernel update never rewrites it. Root is found through the fixed subvolume path `/@`; nothing sets the btrfs default subvolume. Fedora's `limine.conf` comes from stackific-boot's plugin instead, with the same header and one such entry per kernel on the ESP, newest first, titled `<NAME>` and then `<NAME> (<version>)`. On aarch64 its entries are `protocol: efi` with `path: boot():/vmlinuz-<version>` and `cmdline: initrd=\initramfs-<version>.img <command line>`: Fedora's aarch64 kernel is a zstd EFI zboot image, which Limine's `linux` protocol refuses (it checks for a raw arm64 Image; Limine issue 518), so Limine starts it as an EFI program, which decompresses itself and loads the initramfs named by `initrd=` from the ESP it came from.
   - Fedora: SELinux labels for everything the installer wrote (the user's home, `/etc/fstab`, greetd's config, the MangoWM config, `/etc/kernel/cmdline`): `setfiles -r <target>` with the target's own file contexts on `/` and every subvolume's mount point (setfiles does not cross into other mounts), leaving out `/boot` (FAT holds no labels) and the mounted `proc`, `sys`, `dev` and `run`. No `/.autorelabel`, so the first boot needs no extra restart.
   - The firmware entry, last, so an earlier failure leaves none: `efibootmgr` lists the entries, and each one that starts `\EFI\limine\BOOTX64.EFI` from a partition GUID no present partition has (`lsblk --output PARTUUID`; an earlier install a reinstall wiped) is deleted; then `efibootmgr --create --disk <drive> --part <ESP's number> --label "<NAME>" --loader '\EFI\limine\BOOTX64.EFI'`, which puts it first in `BootOrder` and keeps every other entry after it. Nothing else writes NVRAM, at boot or on updates.
9. **End**: `umount --recursive` of the target, whatever happened.

`stackific-boot` (on every image and kept on installed systems) keeps Limine current. On Arch (`arch/packages/stackific-boot/`) it depends on `limine` and `efibootmgr` and ships one pacman hook, `/usr/share/libalpm/hooks/stackific-limine.hook`: after an upgrade or reinstall of `limine`, it copies the machine's program (`BOOTX64.EFI`, or `BOOTAA64.EFI` when `uname -m` is `aarch64`) from `/usr/share/limine/` over both ESP copies, and does nothing where `/boot/EFI/limine/` is missing (the live session). The `limine` package ships no hook of its own. On Fedora (`fedora/packages/stackific-boot/`) it requires `limine` (from Terra), `efibootmgr`, `dracut` and `systemd-udev` and ships:

- `/usr/lib/kernel/install.conf.d/50-stackific.conf`: `layout=other` (kernel-install writes no Boot Loader Spec entries, which Limine cannot read) and `BOOT_ROOT=/boot`.
- `/usr/lib/kernel/install.d/90-stackific-limine.install`, which kernel-install runs after Fedora's dracut plugin on every kernel install and removal, from the kernel package's scriptlets too: on `add` it copies the kernel to `/boot/vmlinuz-<version>` (and a given initrd to `/boot/initramfs-<version>.img` when dracut built none), on `remove` it deletes the kernel and its `symvers`; then it writes `limine.conf` anew (a temporary file, then `mv`) from every kernel on the ESP that has its initramfs, sorted `sort -rV`, with os-release's `NAME` and `/etc/kernel/cmdline`, followed by `/etc/kernel/limine-windows.conf` when the installer left one; the entry's form follows `uname -m` (above). It does nothing where `/etc/kernel/cmdline` or `/boot/EFI/limine/` is missing (the live image and its build). Glue, because no Fedora or Terra package writes Limine entries, and limine-entry-tool is AUR-only. Fedora keeps three kernels (dnf5's `installonly_limit`), so Limine's menu lists up to three.
- An RPM trigger on `limine`, the counterpart of the pacman hook: after limine is installed or upgraded, it copies the machine's program from `/usr/share/limine/` over both ESP copies where `/boot/EFI/limine/` exists.

Each command and its output go to `/run/stackific-installer.log` on the screens and to stderr when unattended. stdin, which carries the password, is never logged.

Exit status: 0 installed; 1 a step failed after the confirmation; 2 refused or invalid answers (nothing written); 3 left before the confirmation (nothing written); 130 stopped by the user.

### What it refuses

- A drive that is not a whole disk (`lsblk` type `disk`, not zram), is an Intel RST RAID member (lsblk's `FSTYPE` `isw_raid_member`, checked before the in-use checks, because md may hold it), is read-only, holds the live medium (found from `/run/archiso/bootmnt` or `/run/initramfs/live`), is under 40 GiB, or has anything mounted or used as swap.
- Free space unless the GPT is clean (`sfdisk --verify` says `No errors detected.` and warns about nothing), the protective MBR has only its `ee` entry (no hybrid MBR), and the largest aligned gap is at least 40 GiB. On an MBR table with a type 7 partition that lsblk sees as NTFS or BitLocker, the reason is BIOS-mode Windows (convert with `MBR2GPT.EXE`), which our UEFI-only Limine cannot start. Such a drive can still be erased. BitLocker no longer refuses the free space: the typed confirmation replaces the refusal.
- An install while BitLocker is on a drive it keeps, until `I have my key` is typed (or set in the unattended file).
- A user name that is not `^[a-z_][a-z0-9_-]{0,31}$` or that the live root already has (`live` excepted), a computer name that is not `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$`, an empty password or one too easy to guess (zxcvbn, the `zxcvbn` crate, below score 3 of 4, with the full name, user name, computer name and os-release's `NAME` counted as guessable: it is also the disk passphrase), an unknown XKB layout or timezone, and an erase whose confirmation is not the drive's kernel name.

## The unattended file

```toml
[disk]
device = "/dev/vda"
mode = "free-space"    # or "erase"
erase = "vda"          # with mode = "erase" only: the typed confirmation, the device's kernel name
bitlocker = "I have my key"  # needed when BitLocker is on a drive the install keeps

[system]
keyboard = "de"        # an XKB layout code from evdev.lst
timezone = "Europe/Berlin"
hostname = "stackific-test"

[user]
full_name = "Test User"
name = "tester"
password = "…"
```

Run it with `stackific-installer --config <file>` as root. Unknown keys are refused.

## Where it runs

- **Desktop shortcut**: on Plasma's desktop, a link in `live`'s `~/Desktop` (`arch/iso/airootfs/home/live/Desktop/`) to the launcher below. Plasma trusts it because its real path is in the system's applications. The install removes it with `/home/live`; MangoWM has no desktop icons, and GNOME lists the installer first in its dash instead (`favorite-apps` in stackific-desktop's gschema override on Fedora).
- **Launcher**: `/usr/share/applications/stackific-installer.desktop` ("Install Stackific OS"), rendered from `installer/stackific-installer.desktop.in` and `branding/branding.env`. It opens foot at 11 points with `dpi-aware=yes`, so the text has the same physical size on every monitor, and runs `run0 stackific-installer`. run0 asks polkit; `live`'s password is empty, so Enter. One terminal for every desktop: foot is on both images, and MangoWM's launcher, Plasma's menu and GNOME's dash and app grid list the file. GNOME Shell is GNOME's polkit agent.
- **Boot menu**: "Install Stackific OS" (`arch/iso/efiboot/loader/entries/02-stackific-install.conf`) next to "Try Stackific OS", which stays the default. It adds `systemd.unit=stackific-installer.target`, which boots `multi-user.target` without the greeter and starts `stackific-installer-console.service`: `stackific-installer --console` as root on tty1 (`TTYPath=/dev/tty1`, getty conflicts with it). However it ends, `ExecStopPost` isolates `graphical.target`, so the live desktop starts. A target and a service are the glue because no packaged tool starts a program on tty1 from a boot entry. Leaving (3) and stopping (130) count as success for the unit. On Fedora the entry is in the ISO's GRUB menu: "Try Stackific OS (<arch>, UEFI)", the default, and "Install Stackific OS (<arch>, UEFI)", which `fedora/iso/edit-boot.sh` (kiwi's `editbootconfig` script) copies from kiwi's live entry with `systemd.unit=stackific-installer.target` added, `<arch>` being `x86_64` or `aarch64`, as on Arch.

## The Base interface

`installer/src/base.rs` holds what differs per base, behind the `Base` trait: the live root (Arch: `/run/archiso/airootfs`; Fedora: `/run/rootfsbase`), the live medium's mount point (Arch: `/run/archiso/bootmnt`; Fedora: `/run/initramfs/live`), the base's own live state (files to remove, commands to run), what puts the kernel and its initramfs on the ESP (files to write, commands), the kernel's and initramfs' file names when the installer writes `limine.conf` itself (Arch; `None` on Fedora, whose kernel-install plugin writes it), and commands after every write (Fedora: the SELinux relabel). The installer picks the base from os-release's `ID_LIKE` (`arch` or `fedora`). Limine's program, the kernel command line (`boot::cmdline`), Arch's `limine.conf` and the firmware entry are shared (`installer/src/boot.rs`).

Every external command and file goes through the `Runner` trait (`installer/src/run.rs`): `Real` on a live system, `Fake` in the tests and the demo, which answers from rules and an in-memory file table and records any command it was not told to expect.

## The screens

Display, Welcome, then six steps: Keyboard, Timezone, You, Drive, Space (with BitLocker after it when needed), Confirm; then Installing, and Done or Stopped. The frame is exactly 80 × 24, centered, so it reads the same on an ultrawide monitor, a 13-inch laptop or a full-screen console; a smaller terminal shows only "make the window bigger or the text smaller". Every screen's text is a fixture in `installer/fixtures/screens/`, which the snapshot tests compare with what ratatui renders; the prompt-trail entry shows them.

- **Display** comes first. On the console, Text size is the console font (`setfont`): the first pick goes by the framebuffer's height (`/sys/class/graphics/fb0/virtual_size`: under 1000 pixels Small, 8 × 16; under 1500 Medium, 12 × 22; under 2200 Large, 16 × 32; else Extra large, 24 × 32), lowered to a size that leaves at least 80 × 24 characters, and ←→ sets another at once. In foot, Text size names foot's own Ctrl and + and −. Motion is Full or Reduced (the console's default), Contrast Standard or High.
- **Keyboard** and **Timezone** share one type-to-search list: the layouts from evdev.lst by code and name, the zones from `timedatectl list-timezones`, ignoring case; an exact code first, then shorter names; an empty search starts with `us` or `UTC`.
- **You**: the user name follows the name's first word until edited; passwords show as dots; a password too easy to guess is refused ("Too easy to guess"), and the help says it also unlocks the disk; with a layout other than the live session's `us`, the help says the password is typed with `us` here and with the chosen layout at every start, so it should use only characters on the same keys in both; the first problem shows under the fields as you type, and "Enter next" appears once every field is valid.
- **Drive** lists whole disks with their largest free space, and each left-out drive with its reason. When Intel RST hides NVMe drives (`/sys/module/ahci/drivers/pci:ahci/*/remapped_nvme` above 0, subiquity's check) or a drive is an RST member, a line says to set the firmware's storage mode to AHCI and prepare Windows first. It reads the drives again each time it shows and when the terminal regains focus, so changes made in Disks show up.
- **Space**: "Use the free space" first when usable, otherwise its line says why; a drive with no partition table offers only the erase.
- **BitLocker**, only with a BitLocker volume on a drive the install keeps, still "5 of 6": Secure Boot is off, so Windows will ask for its recovery key unless BitLocker was suspended; each volume with its state and recovery key IDs (as many as fit, then how many more), the advice to stop and make a key when none exists, where to find the key, and the typed `I have my key`. Esc goes back to Space.
- **Confirm** shows what is on the drive now and afterwards, and the answers; the system partition as `LUKS2` with "btrfs inside" and a line saying the password unlocks it at every start; with Windows found, "Limine's menu will also start Windows." Free space installs on Enter; an erase needs the drive's kernel name typed first.
- **Installing** lists the steps and the copy's progress bar; Ctrl+C asks first (the stop dialog), and Enter there stops the install.

## Design

The screens follow a design guide distilled from Apple's WWDC talks (*Designing Fluid Interfaces*, *The Details of UI Typography*, *Principles of Great Design*), adapted to a terminal. Its rows are soft requirements; every spacing, colour and timing is a named constant in `installer/src/ui/theme.rs`, with a comment saying why.

| The guide | In the installer |
| --- | --- |
| Response | Every key and mouse event is handled and redrawn in the same frame, with no debounce. A search filters on each keystroke. The install runs on its own thread. |
| Direct manipulation | In foot, a press highlights a row or a bottom-border action, the release commits it, and moving off first cancels. The wheel moves a list. The console has no mouse. |
| Interruptibility, velocity handoff | One spring model (`ui/motion.rs`); a retarget keeps position and velocity, so Esc mid-slide reverses without a jump. |
| Springs | Critically damped (no bounce): slides 0.3 s, the selection marker 0.15 s, the progress bar 0.4 s (never backwards), the rubber band 0.2 s. Up to 60 frames per second, and none while nothing moves. |
| Momentum | A held ↑ or ↓ moves three rows per repeat after half a second. A wheel flick carries on by the guide's projection (deceleration rate 0.99). |
| Spatial consistency, hint the direction | Forward slides the next screen in from the right, Back from the left. The marker glides toward the row it goes to. The stop dialog grows out of the bottom border's "Ctrl+C stop" and shrinks back into it. |
| Rubber-banding | Past a list's edge, a press nudges the list one row and springs it back. |
| Smoothness | ratatui redraws only changed cells; motion moves at most one cell per frame; the bar moves in eighths of a cell (halves on the console). Slides cover six columns, so the direction shows without the text racing past. |
| Materials and depth | In a true-colour terminal (`COLORTERM=truecolor`, or `TERM=foot`, which run0 passes on while it drops `COLORTERM`): the frame's surface is the accent at 6 % over foot's default background, the bottom border a heavier band, the dialog sits on a dim scrim with a one-cell shadow, and a scrolled list fades its edge rows. None of it with High contrast or `NO_COLOR`. |
| Sound | One bell, on the frame that shows Stopped. |
| Reduced motion, contrast, colour | Reduced: slides, glides, the band and the dialog's growth are instant; the bar still moves. High contrast: no dim text, no tints, bold and reverse video. `NO_COLOR` removes all colour. A selection is reverse video, never colour alone. On the console (`TERM=linux`) the markers become ASCII and the arrows words. |
| Typography | The system's monospace font; titles bold, body regular, help dim; prose wraps at 75 columns with no one-letter word at a line end; sizes right-aligned with one decimal and a unit. |
| Purpose, agency, responsibility | No manual partitioning, no language screen. Confirmations only where data is at stake: the typed name before an erase, Enter on the free-space summary, the stop dialog. A before-and-after summary, refusals that say why, and a password never echoed or logged. |
| Familiarity, flexibility | Arrows, Tab and Shift+Tab, Enter, Esc, Home, End, Page Up and Down, and the mouse; the same key means the same everywhere. The desktop or the console; text size, motion and contrast. |
| Wayfinding | The top border names the program and "n of 6 · Step"; the bottom border lists only the keys that work, by what they do. Esc goes back, and on the first two screens leaves (on the console, to the live desktop). Ctrl+C leaves at once before the install and asks during it. |
| Process | `just installer demo`, and `--slow`. |

Dropped or narrowed from the guide, and why:

- The slides cover six columns, not a whole screen: a full 80-column slide in 0.3 s moves several columns per frame, which reads as a jump in a terminal. The short slide keeps "at most one cell per frame".
- The terminal's own background colour is assumed (foot's default) rather than read: reading it needs an escape-sequence round trip that would delay the first frame.
- Haptics: none in a terminal.

### Unlock and the boot-failure screen

Every boot asks for the disk passphrase on the console, after Limine's menu, with the keyboard layout from `/etc/vconsole.conf` (`sd-vconsole` on Arch, dracut's i18n module on Fedora). systemd-cryptsetup gives 3 tries. After that the initramfs would start `emergency.service`, systemd's emergency shell, which says the root account is locked; stackific-boot replaces it in the installed system's initramfs only with `/usr/lib/stackific/boot-failure` (`installer/initramfs/`, a POSIX `sh` script): a cleared screen saying the start failed, that a disk password typed wrong 3 times is the usual cause, to check Caps Lock and the keyboard layout, and Enter to restart. A drop-in (`stackific-boot-failure.conf`) replaces `ExecStart` of `emergency.service` and `rescue.service`; Arch's mkinitcpio hook `stackific-boot-failure` and Fedora's dracut module `99stackific-boot-failure` (host-only builds only, so not the live image's) put both into the initramfs. Glue, because neither initramfs tool has such a screen. Passphrase only: no TPM2 or FIDO2 enrolment (BT-06).

Tests: `just <base> test-install` boots the installed system with systemd's `cryptsetup.passphrase` credential (SMBIOS type 11, `STACKIFIC_TEST_PASSPHRASE` in `tests/vm/boot.sh`), then once more without it, where `tests/vm/unlock.sh` types three wrong passphrases, checks the boot-failure screen does not restart by itself, presses Enter, and types the password (`test_password` in `tests/vars.just`) on the German layout.

## Later

- Typing the password in the chosen layout on the You screen (today the live session's `us`; the help warns when the layouts differ).
- A separate disk password ("use a different disk password"), and changing the disk passphrase with the login password: today `passwd` leaves the disk's as it was.
- Plymouth for the passphrase prompt; TPM2 plus PIN or FIDO2 once Secure Boot works with Limine.
- Windows and BitLocker on drives the installer leaves out (under 40 GiB, read-only, in use): they are not looked at.
- The BitLocker screen shows the volumes that fit and counts the rest; the unattended refusal lists all.
- Real Windows with BitLocker and a TPM (swtpm), across a Limine update: the real-hardware checklist (task 030).
- Arch Linux ARM's `/boot/dtbs`: the install copies only `/boot/Image` from the boot medium, so `pacman -Qk linux-aarch64` reports the device trees missing until the kernel's next upgrade writes them. ACPI machines (UEFI arm64 laptops, QEMU's `virt`) do not need them.
- Re-create a lost firmware entry on updates; today the fallback path covers a whole-drive install, and the firmware's boot menu covers the rest.
- Limine's menu in our look (a wallpaper and colours with enough contrast).
- A free-space guard on the ESP once several kernels share it (`linux-lts`, task 019; Fedora's three kernels take about 170 MiB of its 4 GiB: 19 MB of kernel and 37 MB of initramfs each).
- Terra's packages on installed Fedora systems (`limine`, `mangowm`, `noctalia-greeter`): the image keeps no Terra repo file, so dnf5 updates them only once our repos are online (task 028).
